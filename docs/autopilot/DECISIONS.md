## Human note — 2026-09-17 (Phase F review, host-side sandbox fixes)

Two sandbox defects found while running the host gate. Neither is a Phase F
deliverable defect; both are in `sandbox/run.sh` and were fixed on the host.

**1. `frontend/node_modules` was shared between host and container.** The F.2
note above states the sandbox gives the container its own `node_modules` volume.
It did not: commit `2960874`, titled "restore frontend overlay volumes and fix
volume ownership", changed only this file and never touched `run.sh`. The two
environments shared one tree through the repo bind mount, so whichever ran
`npm ci` last won and broke the other (npm/cli#4828 — a Linux install leaves the
host without `@rollup/rollup-darwin-arm64`). Observed live: a host `npm ci`
broke the F.9 sandbox session, whose own `npm ci` then broke the host.

Fixed with a `--mount ... volume-nocopy=true` overlay plus an `ensure_volumes()`
that chowns the volume to the caller. `volume-nocopy` is required: Docker seeds
an empty volume from whatever is at the mount path, which here is the host tree,
so a plain `--volume` would copy the mismatch straight in. This is the node
counterpart to `UV_PROJECT_ENVIRONMENT`, which already protects `backend/.venv`.

**2. `sandbox/run.sh verify` destroyed uncommitted work.** Its commit-to-main
probe ran `git commit --allow-empty` followed by `git reset --hard HEAD~1`. On
any branch other than `main` the commit legitimately succeeds, so the probe
reported a false `guard FAILED` and then hard-reset the bind-mounted repo,
deleting uncommitted changes — it ate this very fix once before it was
committed. Now `reset --soft` (the probe commit is empty, so this restores the
prior state exactly) and the message distinguishes "not exercised on this
branch" from a real failure.

## Human note — 2026-09-18 (milestone 1.4 review): the search index rowid ceiling

Recorded at the 1.4 gate because it is a constraint nobody chose explicitly and
the phase that trips over it is several phases away.

`search.py` encodes document identity as `source id * 4 + kind code`, which is
why the contentless index needs no mapping table beside it. The encoding is
documented in that module's docstring, repeated by the migration's nine
triggers, and pinned by `tests/test_search.py`. It is a good design for the
three types that exist today (timeline entries, notes, comments).

**It hard-caps the index at four document types.** Phase 4 adds attachments and
Phase 5 adds inbound email, both plausibly searchable. The fourth slot absorbs
one of them; the fifth has nowhere to go.

This is not treated as a defect and no change is asked for now. A contentless
FTS5 index stores no copy of the source text, so it is rebuildable from the
source tables by construction — `make reindex` already does exactly that, and
`test_rebuild_reproduces_the_index_the_migration_built` proves the rebuild
matches what the migration produced. So widening the encoding (to `* 8`, or to
an explicit `(kind, id)` pair) is a migration that rewrites rowids and reindexes,
not a data-loss risk.

**Action for whichever milestone first needs a fourth or fifth searchable type**
(4.x attachments, or 5.x email): widen the encoding as part of that milestone
rather than working around the ceiling, and log the choice. Check
`test_writes_are_indexed_under_the_documented_rowid`, which asserts the current
scheme and will fail first.
